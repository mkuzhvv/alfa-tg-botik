# Архитектура

Один Spring Boot-проект, один Maven-модуль, один Java-контейнер. Организация кода повторяет `credit-cabinet`.

## Компоненты

| Компонент | Ответственность |
|---|---|
| Java 21, Spring Boot, Spring AI | Telegram, API, консультации, поиск, проверка ответов и бизнес-операции |
| Mini App | План, напоминания и профиль |
| PostgreSQL с pgvector | Исходные данные, состояние приложения и поисковый индекс |
| Готовая модель | Генерация через API или отдельный сервер модели |
| ML-инструменты | Подготовка корпуса, выбор моделей, инструкции и проверка качества |

Spring AI подключает модель и векторный поиск. Самостоятельный Python API консультаций не требуется. ML 1 выбирает embedding-модель и фиксирует её версию/размерность; ML 2 выбирает генеративную модель и способ запуска. Бэкенд подключает их через Spring AI.

## Java-пакеты

| Пакет | Ответственность |
|---|---|
| `identity` | Пользователь, профиль бизнеса, авторизация и текущая идентичность |
| `telegram` | Сообщения, команды, кнопки и отправка ответов |
| `catalog` | Метаданные материалов, доступность и импорт |
| `assistant` | Диалог, контекст, RAG, интеграция с моделью и проверка результата |
| `plan` | Цель, шаги и прогресс |
| `reminder` | Расписания и исполнение напоминаний |
| `common.error` | Общий формат ошибок |
| `config` | Настройки Spring, интеграций, часов и пулов |

Внутри функции используются `api`, `service`, `model`, `persistence`. В `assistant` есть `integration` и `retrieval`, в `reminder` — `scheduling`. Контроллеры и Telegram-обработчики вызывают одинаковые бизнес-сервисы. Долгие вызовы модели выполняются вне транзакции БД.

## Базы

В одном PostgreSQL две базы. `alfa_source` хранит восстановленный оригинальный бэкап и используется подготовкой данных. Основной datasource Java — `assistant`, со схемами `app` и `knowledge`.

Flyway управляет собственными схемами и таблицами; Hibernate использует `validate`. Восстановление оригинального бэкапа выполняется отдельно через `pg_restore`. Java импортирует подготовленный экспорт, рассчитывает embeddings и сохраняет индекс. При смене embedding-модели индекс перестраивается.

## Обработка

Консультация: Telegram → профиль и история → поиск разрешённых фрагментов → Spring AI → проверка результата → ответ и сохранение истории. Модель предлагает действия, Java проверяет параметры; создание плана и напоминания требует подтверждения пользователя.

Mini App запускает генерацию плана по явному действию. При замене Java сверяет ID и версию активного плана до вызова модели и при сохранении. Транзакция сохраняет новый план, архивирует прежний и записывает результат команды для идемпотентного повтора. БД обеспечивает единственный активный план на пользователя.

Каждый диалог принадлежит пользователю. История хранится в БД, в контекст модели передаётся ограниченная часть. Запросы одного диалога обрабатываются последовательно. Общий бюджет консультации — 60 секунд, включая возможное исправление формата.

Напоминания исполняются Java через Quartz с JDBC-хранилищем. Время отправки хранится в UTC, правило повторения — с локальным временем и IANA-зоной. Перед отправкой проверяются актуальные состояние и версия.

## Доступ и запуск

Mini App передаёт Telegram `initData` бэкенду и получает токен сессии. Все пользовательские API используют `Authorization: Bearer <token>`. Telegram-события определяют пользователя по Bot API; произвольный `userId` из HTTP-тела не является авторизацией.

Nginx отдаёт интерфейс и проксирует `/api` в Java. Публичный Mini App использует HTTPS. Бот получает события long polling. `compose.yaml` находится в корне, Dockerfile и настройки — в `dockerfiles/`. Постоянные данные — в томе PostgreSQL. Токены и ключи передаются настройками.
