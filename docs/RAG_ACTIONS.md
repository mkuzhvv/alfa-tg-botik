# Планы, напоминания и профиль: actions-1

Реализация контракта ML 2 от 15 ноября 2026. Публичная schemaVersion остаётся
`0.1.0`; версия инструкций — `consultation-7`, дополнительная ветка — `actions-1`.
Общий запуск и Java ProcessBuilder: [RAG_BACKEND_INTEGRATION.md](RAG_BACKEND_INTEGRATION.md).

## Граница действий

Python возвращает предложение. Он не пишет профиль/план в БД, не архивирует
предыдущий план, не ставит задачу Quartz и не отправляет Telegram-сообщения.

Java проверяет права, структуру, версии и допустимость ID. План и напоминание
сохраняются только после подтверждения пользователя. Предложение плана хранится
24 часа; замена ACTIVE-плана требует отдельного подтверждения. Профиль сохраняется
Java по явно сообщённым полям с проверкой текущей версии, а не по тексту ответа.

Все поля response присутствуют во всех статусах:
`schemaVersion`, `status`, `answer`, `sourceChunkIds`, `recommendations`,
`profilePatch`, `planProposal`, `reminderProposal`.

| Статус | Объекты |
|---|---|
| ANSWER | Есть источник; может быть planProposal; reminderProposal=null |
| CLARIFY | Один уточняющий вопрос; sources пусты, предложения=null |
| NOT_FOUND | Не хватает материалов; sources пусты, предложения=null |
| ACTION_PROPOSAL | Полное reminderProposal; planProposal=null |

profilePatch может сопровождать любой результат, если пользователь явно сообщил
новые сведения. Пустой профиль сам по себе не требует уточнения.
Технический сбой не преобразуется в NOT_FOUND.

## Серверное время и вход bridge

Сервер Java передаёт свежее `now` в UTC, не берёт его из HTTP-тела фронтенда:

```json
{
  "requestId": "demo-reminder",
  "schemaVersion": "0.1.0",
  "now": "2026-11-15T10:00:00Z",
  "operation": "consultation",
  "message": "Напомни завтра в 9 утра продолжить курс",
  "profile": {"timeZone": "Europe/Moscow"},
  "history": [],
  "currentPlan": null
}
```

В stdin JSON отправляется одной строкой с LF. `now` необязателен для совместимости:
при отсутствии используется UTC-clock worker. Если указан, он должен быть строкой
с Z или +00:00. `operation` — consultation (по умолчанию) либо generate_plan.
Неизвестные значения отвергаются. Формат envelope ok/result/error прежний.

Для времени из примера «завтра» — 16 ноября в зоне пользователя, а не дата UTC+1
без учёта зоны. Местоположение «живу в Москве» автоматически не задаёт timeZone.
Зона берётся из подтверждённого profile.timeZone, из явного «по Москве»/IANA-зоны
в запросе либо из ответа пользователя на вопрос о зоне.

## Напоминания

Полный фрагмент result.response для входа выше:

```json
{
  "schemaVersion": "0.1.0",
  "status": "ACTION_PROPOSAL",
  "answer": "Предлагаю напомнить 16.11.2026 в 09:00 (Europe/Moscow). Сохранение и отправка — после подтверждения в приложении.",
  "sourceChunkIds": [],
  "recommendations": [],
  "profilePatch": {},
  "planProposal": null,
  "reminderProposal": {
    "title": "продолжить курс",
    "schedule": {
      "type": "ONCE",
      "at": "2026-11-16T06:00:00Z",
      "timeZone": "Europe/Moscow"
    },
    "materialId": null,
    "planStepId": null
  }
}
```

Поддержанные формы и результат при now из примера:

| Сообщение | Тип и значимые поля |
|---|---|
| «Напомни завтра в 9 утра» | ONCE, at=2026-11-16T06:00:00Z |
| «Напомни через 30 минут» | ONCE, at=2026-11-15T10:30:00Z |
| «Напоминай ежедневно в 09:30» | DAILY, localTime=09:30, startDate=2026-11-15 |
| «Напоминай каждый понедельник в 18:00» | WEEKLY, dayOfWeek=MONDAY |
| «Напоминай ежемесячно 31-го числа в 09:00» | MONTHLY, dayOfMonth=31 |
| «Напоминай в последний день месяца в 09:00» | MONTHLY, dayOfMonth=31 |

Каждое расписание содержит timeZone. Для повторений startDate — нижняя граница;
Java вычисляет ближайшую будущую отправку. Число 31 не заменяется на 28/30:
сдвиг на последний день короткого месяца и восстановление 31 в следующем месяце
выполняет планировщик Java. Время DAILY/WEEKLY/MONTHLY сохраняется местным.
Для ONCE неоднозначное осеннее время использует первое вхождение, весенний
пропуск сдвигается вперёд; для повторений это правило исполняет Java при расчёте.

Если времени/даты/зоны не хватает, возвращается CLARIFY с одним вопросом.
История USER/ASSISTANT позволяет продолжить уточнение в несколько ходов.
Необходимо передавать историю при каждом запросе: worker её не хранит.
Невозможные даты, прошедшее разовое время, несколько вариантов через «или»,
несколько дней недели и неподдержанные интервалы не превращаются в догадку.
Для «напомни уплатить налог» срок не выводится из taxRegime: спрашивается дата.
Java повторно проверяет ONCE.at относительно своего свежего времени при
подтверждении: предложение могло устареть за время ожидания. Смена зоны профиля
не переносит уже сохранённые напоминания автоматически.

Парсер ориентирован на явные русские формулировки; неизвестные формы требуют уточнения.

`materialId` может быть null либо ID доступного материала. `planStepId` — null
либо ID шага текущего ACTIVE-плана. «О втором шаге» связывается с position=2.
Чужой/неизвестный ID, отсутствующий номер шага и несовместимые materialId/planStepId
дают уточнение. При обоих ID материал должен входить в этот шаг.

Отмена, перенос и изменение уже сохранённого Reminder не представлены этим
контрактом предложения: для них Java маршрутизирует собственные CRUD-операции.
Python не выдаёт новое напоминание вместо команды отмены и не подтверждает отмену.

## Планы

Для `/plans/generate` Java сначала выбирает goal из HTTP-запроса либо
profile.currentTask, проверяет длину 1–250 и конфликт замены плана. Затем передаёт:

```json
{
  "requestId": "demo-plan",
  "now": "2026-11-15T10:00:00Z",
  "operation": "generate_plan",
  "message": "Увеличить повторные покупки в кофейне",
  "profile": {"industry": "кофейня", "businessStage": "OPERATING"},
  "history": [],
  "currentPlan": null
}
```

В чате operation можно опустить: «Составь план увеличения повторных покупок»
распознаётся как запрос плана. По умолчанию создаются три шага; явные
«из 4 шагов»/«из 5 шагов» поддержаны в пределах контракта 3–5.
Без понятной цели задаётся вопрос. Если материалов для содержательных шагов
недостаточно — NOT_FOUND. Фиктивный план без источников не создаётся.

В успешном response:

- status=ANSWER, sourceChunkIds содержит использованные фрагменты;
- planProposal.goal — явно выбранная пользователем цель;
- planProposal.steps — 3–5 объектов title, description, materialIds;
- title до 160, description до 600, materialIds содержит 1–2 доступных ID;
- текущая реализация связывает каждый шаг с одним материалом его источника;
- descriptions берутся из проверенных абзацев; заголовки формирует модель;
- recommendations содержит объяснения для использованных материалов, не более трёх;
- reminderProposal=null. Одновременный запрос плана и напоминания требует выбора.

Новые ID плана/шагов и их версии выдаёт Java при сохранении. Python не выдумывает
persisted ID для planProposal. При текущем ACTIVE-плане новый объект остаётся
предложением замены; старый план не меняется. Ошибка генерации не должна удалять
или архивировать прежний план. Java повторно проверяет версию перед транзакцией
сохранения и защищает повтор операции Idempotency-Key.

Внутри model call используется компактный формат title/evidenceId. Источники,
UUID и описания восстанавливает адаптер plan_proposals.py; одно копирование
промпта без этого адаптера не воспроизводит публичный контракт.

## currentPlan

Java передаёт свой Plan DTO из БД, не объект из произвольного frontend-запроса.
Обязательны id, goal, status (ACTIVE/ARCHIVED), version и 3–5 steps.
createdAt/updatedAt принимаются как UTC-строки. В каждом шаге:

```json
{
  "id": "00000000-0000-4000-8000-000000000002",
  "position": 2,
  "title": "Настроить сбор обратной связи",
  "description": "Изучить материал и подготовить проверку результата.",
  "status": "TODO",
  "materials": [
    {
      "id": "00000000-0000-4000-8000-000000000111",
      "title": "Пример карточки",
      "kind": "ARTICLE",
      "description": null,
      "recommendationReason": null,
      "isPaid": false,
      "duration": null,
      "url": "https://kurs.alfabank.ru/articles/synthetic/"
    }
  ]
}
```

Это синтетический пример структуры, а не действующий ID/URL каталога. В реальном
запросе используются ID и карточки из серверной БД. Позиции идут от 1 без
пропусков, ID шагов уникальны, каждый шаг содержит 1–2 карточки.

Для короткого «Что делать дальше?» поиск использует цель и следующий TODO-шаг.
Модель видит цель, описания и статусы и получает инструкцию не повторять
выполненное. Если все шаги DONE и пользователь спрашивает, что дальше,
возвращается вопрос о новой цели; план не запускается заново.
DONE/TODO, принадлежность плана и отметки выполнения сохраняет Java; после
изменения нужно передать актуальный currentPlan на следующем ходе. Архивный план
не используется как текущая активная цель и не предоставляет ссылки для нового
напоминания на его шаг.

## profilePatch

Например, сообщение «У меня пекарня. Я новичок. Мой налоговый режим УСН 6%.»
может дать:

```json
{"industry":"пекарня","experience":"BEGINNER","taxRegime":"USN_6"}
```

Это фрагмент profilePatch, не весь response. В pure profile-запросе status=CLARIFY:
ответ предлагает изменение и спрашивает следующую бизнес-задачу, sourceChunkIds
пуст. В консультации тот же patch может сопровождать ANSWER с источниками.

Обновляются только явно сообщённые поля: industry, currentTask, timeZone,
businessStage, experience, taxRegime. Наличие кофейни само по себе не заполняет
стадию/опыт/налоговый режим. Примеры про знакомых и условное «если бы у меня была
кофейня» не меняют профиль. «Раньше X, теперь Y» допускает только актуальную фразу.
Смена timeZone отдельного напоминания не меняет автоматически зону профиля.

null предлагается лишь для явной просьбы очистить конкретное поле. Например,
при известной industry «Удали сферу бизнеса из моего профиля» даёт industry=null.
Отсутствие сведений не приводит к очистке существующего значения. Уже совпадающие
значения повторно не предлагаются. Java сохраняет только полученный patch,
с учётом версии профиля; не заменяет весь профиль частичным объектом. Различайте
отсутствующий ключ и явный null: настройка сериализации NON_NULL не должна
выкидывать запрос очистки, а полный Profile DTO не должен добавлять null для
всех отсутствующих полей.

Внутренний extractor возвращает field/value/evidence. evidence проверяется
по точным словам текущего USER-сообщения, дополнительно отбрасываются догадки,
гипотезы, третьи лица, отрицания и неподтверждённые enum/zone. Текст ASSISTANT
не является доказательством изменения. При переносе в Spring AI нужно портировать
эту проверку из profile_updates.py, а не доверять произвольному profilePatch модели.

## Валидация и бюджет

feature_contract.py формирует полную response_schema и проверяет:
типы/длины, 3–5 шагов, допустимые материалы, 1–2 материала шага, все четыре типа
расписания, будущий ONCE.at, IANA-зону, принадлежность planStepId текущему плану,
совместимость materialId/planStepId, исключение одновременного плана и напоминания,
отсутствие URL/SQL/fences и утверждений «сохранено/создано».

На все вызовы модели в одном запросе действует общий deadline 60 секунд.
Исправление формата разрешено один раз суммарно: если extractor профиля уже
потратил повтор, planner/консультация не получает ещё один независимый повтор.
Тайм-аут остаётся технической ошибкой envelope ok=false.

Проверки:

```sh
.venv/bin/python -m unittest discover -s ml -p 'test_*.py'
.venv/bin/python ml/rag.py ask data/processed/2026-11-13-local 'Напомни завтра в 9 по Москве продолжить курс' --now 2026-11-15T10:00:00Z
.venv/bin/python ml/rag.py ask data/processed/2026-11-13-local 'Увеличить повторные покупки' --operation generate_plan --context ml/demo_context.json
```

Исторические 100 вопросов consultation-6 не измеряли новые функции. Их скор не
переносится на actions-1: полностью определённый запрос напоминания теперь должен
давать ACTION_PROPOSAL, а не прежний отказ/уточнение. Новые unit-тесты и живые
сценарии проверяют предложения, расписания и patch; фактическая доставка Telegram
остаётся сквозной проверкой Java/Quartz/Bot API после подключения бэкенда.

## Проверено на текущей реализации

97 синтетических unit-тестов. На локальной Qwen3.5 9B проверены профиль
с тремя явными полями, очистка industry, планы на 3 и 5 шагов, все четыре
расписания, недостающая зона, напоминание по шагу и продолжение текущего плана.
Через настоящий JSONL bridge проверены совмещённый profilePatch + planProposal,
предложение замены ACTIVE-плана и связанное напоминание. Полная комбинация
профиля и плана заняла около 54 секунд, отдельный план на 5 шагов — около 26.
Это локальные проверки предложений, не свидетельство записи в Java-БД или
доставки Telegram. Подробные ответы находятся в приватной data/processed/features-2026-11-15/.
