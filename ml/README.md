# Подготовка данных для RAG

Первая ML-версия: подготовка корпуса, локальный семантический поиск,
генерация консультаций с источниками и рекомендациями. BM25 оставлен для сравнения.
Telegram здесь не реализован.
Рабочая интеграция остаётся в Java/Spring AI; Python не поднимает отдельный API.

## Что нужно

- Python 3.9+; дополнительных Python-библиотек нет.
- Docker Desktop и существующий Compose проекта нужны **только для export**.
- Восстановленная база `alfa_source`. Скрипт её не восстанавливает и не меняет.
- Для семантического поиска/ответов: запущенная Ollama с локальными GGUF-моделями
  `embeddinggemma:300m` и `qwen3:4b`. Пакет Python `ollama` не нужен.

Все команды ниже выполняются из корня `alfa-tg-botik`.
Исходная БД читается одной согласованной транзакцией `READ ONLY`.
Таблицы пользовательской активности, авторов и профилей не выгружаются.
Бэкенд, миграции, конфигурация PostgreSQL и индекс `assistant` не изменяются.

## Быстрый старт с уже подготовленной выгрузкой

```sh
python3 ml/rag.py validate data/processed/2026-11-12-v2
python3 ml/rag.py retrieve data/processed/2026-11-12-v2 'Покупатели не возвращаются. Как это исправить?'
python3 ml/rag.py ask data/processed/2026-11-12-v2 'Как увеличить повторные продажи?'
```

`retrieve` возвращает источники и карточки; `ask` дополнительно вызывает
локальную LLM. В `response` лежат поля контракта, в `references` и
`recommendationCards` — ссылки из каталога, в `diagnostics` — модели, время,
оценки близости и число реально отправленных источников. `score` — не вероятность
правильного ответа. Порог 0.45 пока не откалиброван на независимой разметке.

Если запускаете на другом компьютере, сначала скачайте модели и постройте индекс:

```sh
ollama pull embeddinggemma:300m
ollama pull qwen3:4b
python3 ml/rag.py index data/processed/2026-11-12-v2 --batch-size 32
```

Веса скачиваются из сети; содержимое корпуса используется только на ноутбуке.
Построение индекса выполняется один раз и может занимать несколько минут.
При прерывании повторите ту же команду: уже записанные батчи будут использованы.
Итоговый `semantic.sqlite` не перезаписывается. Для другой модели/версии данных
нужна новая версия корпуса. Смена digest embedding-модели обнаруживается.

Альтернативная модель, поддержанная кодом: `qwen3-embedding:0.6b` через
`index --embedding-model qwen3-embedding:0.6b`. У неё другой query-prefix и
размерность: индексы нельзя смешивать. По пробной проверке на этом ноутбуке
EmbeddingGemma быстрее; полноценного сравнения качества двух моделей пока нет.
Модель генерации меняется через `ask --chat-model ...`. Установленная на ноутбуке
`qwen3.5:9b-q4_K_M` в пробном запуске параллельно индексации превысила 60 секунд;
для первого запуска выбрана меньшая Qwen3 4B. При проверке скорости не запускайте
индексацию одновременно с консультацией.

Лексический baseline остаётся доступен:

```sh
python3 ml/rag.py search data/processed/2026-11-12-v2 'Как удержать клиентов?'
```

Он не учитывает русскую морфологию и возвращает выдержки без генерации.

## Как устроен локальный RAG

`rag.py` отвечает за подготовку данных и CLI; `rag_runtime.py` — за inference.
Это отдельные функции и классы, которые позже можно вызывать из экспериментального
кода. Отдельный HTTP-сервис не поднимается, Java не изменяется.

1. Из полного текста каждого фрагмента и его заголовка вычисляется embedding.
   Отдельно индексируются названия, описания, темы и отрасли карточек каталога.
2. EmbeddingGemma использует документный формат `title: ... | text: ...`,
   а для вопроса — `task: search result | query: ...`. Векторы нормализуются.
   Усечение на стороне embedding API отключено: слишком длинный вход даст ошибку.
3. SQLite хранит float32-векторы, ID, размерность, digest модели и хеш manifest.
   При запросе считаем cosine similarity точным перебором: для текущего небольшого
   корпуса отдельный векторный сервер не нужен. Это ML-индекс, не индекс Java.
4. Источники ищутся среди бесплатных разрешённых текстов; карточки рекомендаций —
   среди каталога, где может присутствовать платный курс без закрытого содержания.
   Результаты источников разнообразятся по материалам.
5. LLM получает вопрос, известный профиль, до четырёх последних сообщений,
   до трёх полных источников и до трёх карточек, отобранных по близости к запросу.
   Описания карточек ограничены 200 символами; платность не исключает карточку.
   При переполнении бюджета сначала удаляется старая история, затем менее
   релевантные карточки и описание оставшейся карточки, затем слабые источники.
   Тексты оставшихся источников не обрезаются. Если минимальный вход не помещается,
   возвращается явная ошибка с просьбой сократить вопрос/профиль.
   Окно контекста (16384) и лимит выхода (1200 токенов) сохранены.
6. Ollama ограничивает генерацию JSON-схемой; дополнительная проверка Python
   контролирует ссылки на ID, статусы, длины, рекомендации и отсутствие действий.
   При ошибке формата допускается одно исправление в общем бюджете 60 секунд.
   Ошибка модели/тайм-аут — техническая ошибка, а не `NOT_FOUND`.
   При валидном `NOT_FOUND` свободный ответ и рекомендации модели заменяются
   фиксированным сообщением: «В доступных материалах не нашлось достаточной
   информации для ответа». Это исключает выдуманные пояснения в отказе,
   но не заменяет проверку достоверности обычных ответов `ANSWER`.

### Короткий формат общения с моделью

Внутри локального runtime модель возвращает четыре поля: `status`, `answer`,
`sourceIds`, `recommendations`. Ответ — до 420 символов с двумя действиями,
рекомендация — максимум одна, её объяснение — до 100 символов.
Это ограничение фактического текста, не изменение `num_predict`: лимит остаётся
1200 токенов, окно — 16384.

Модель видит короткие метки `S1`/`M1` вместо UUID. Адаптер проверяет метки,
восстанавливает исходные ID и добавляет постоянные поля `schemaVersion`,
`profilePatch`, `planProposal`, `reminderProposal`. Публичный результат
и формат для интеграции с Java остаются прежними. Неизвестные метки отклоняются.
При прямом вызове Ollama из Java компактный промпт требует такого же адаптера
коротких ID и полей на стороне интеграции; подключать его к старому парсеру
сырого ответа без адаптера нельзя. Java-код в этой реализации не меняется.

В модель не передаются URL, пустые duration/профиль/история и служебные null-поля.
Тип материала, платность и известная длительность сохраняются для рекомендаций.
Ссылки и полные карточки достраиваются программой. Полные тексты выбранных
источников сохраняются. В JSON контекст расположен перед вопросом;
в конце — вопрос и UTC-дата без меняющихся секунд. Это позволяет
кэшировать одинаковый префикс. Новый набор источников всё равно требует обработки.
Версия промпта — `consultation-3`, внутреннего формата — `compact-1`.

Рабочие статусы: `ANSWER`, `CLARIFY`, `NOT_FOUND`. Используется подмножество
контракта консультаций: `profilePatch={}`, `planProposal=null`,
`reminderProposal=null`. Генерация планов, напоминаний, изменение профиля
и `currentPlan` пока не реализованы. Это задачи следующей версии/интеграции.
Проверка формата и ID не доказывает фактическую обоснованность текста.

Каждый вызов `ask` самостоятельный. Для персонализации можно передать локальный
JSON через `--context data/source/demo_context.json`, например:

```json
{"profile":{"industry":"кофейня","experience":"BEGINNER"},"history":[],"currentPlan":null}
```

История: до 12 объектов `{"role":"USER","text":"..."}` либо `ASSISTANT`.
Предыдущий пользовательский вопрос помогает поиску коротких продолжений диалога.
Данные контекста автоматически не сохраняются и профиль по догадке не заполняется.

## Как проверять качество

Начните с `retrieve`, отдельно от генерации: есть ли в первых пяти результатах
источники с ответом? Затем `ask`: подтверждены ли конкретные утверждения
возвращёнными фрагментами, полезны ли рекомендации, корректно ли уточнение?

В локальном JSONL создайте 20–30 вопросов, для которых вручную нашли ответ
в корпусе. Каждая строка имеет формат:

```json
{"question":"Вопрос своими словами","expectedMaterialIds":["UUID нужного материала из materials.jsonl"]}
```

```sh
python3 ml/rag.py evaluate data/processed/2026-11-12-v2 data/source/quality_cases.jsonl
```

Команда измеряет Recall@5 и HitRate@5 только для источников ответов, не карточек.
Валидатор набора проверяет ID, но автор разметки должен сам проверить содержание.
Небольшой стартовый набор не заменяет независимую разметку.
Локально добавлен `data/source/quality_cases.jsonl` из шести стартовых вопросов:
ожидаемые материалы выбраны по теме и требуют вашей проверки и расширения.

Для ответов отдельно проверьте: обычный вопрос, перефразирование, разные профили,
продолжение диалога, неоднозначный запрос, тему вне базы, запрос закрытого урока,
попытку выдать инструкции за источник и отключённую Ollama. На внебазовой теме
ожидается честный пробел; технический сбой не должен становиться таким ответом.
Запишите результаты и время, не подбирайте порог по всем проверочным вопросам:
оставьте часть вопросов для финальной проверки.

Рекомендуемые ориентиры прототипа, а не доказанные результаты: нужный источник
в топ-5 минимум у 80% размеченных вопросов, отсутствие выдуманных ID/ссылок и
раскрытия закрытых текстов во всех проверенных случаях. Оценку фактов и пользы
делайте вручную; автоматические тесты ниже проверяют поведение кода.

## Как повторить подготовку

1. Выгрузить локальный снимок (файл не должен существовать):

   ```sh
   python3 ml/rag.py export
   ```

   Результат: `data/source/ml_snapshot.json`. При обновлении исходной базы
   укажите новое имя: `export --output data/source/ml_snapshot_v2.json`.
   Snapshot содержит исходные учебные тексты, включая закрытые блоки;
   он предназначен только для локальной подготовки и не передаётся модели.

2. Посмотреть количества и справочники:

   ```sh
   python3 ml/rag.py audit data/source/ml_snapshot.json
   ```

3. Создать **новую** версию подготовленного корпуса:

   ```sh
   python3 ml/rag.py prepare --snapshot data/source/ml_snapshot.json --version my-v3
   ```

   Для воспроизведения текущего отбора используйте `--as-of 2026-11-12T13:05:26Z`.
   Без параметра берётся текущее UTC-время. Существующая версия не перезаписывается.

4. Проверить результат:

   ```sh
   python3 ml/rag.py validate data/processed/my-v3
   python3 -m unittest discover -s ml -p 'test_*.py' -v
   ```

Результаты сохраняются в `data/processed/<версия>/`:

- `materials.jsonl`: карточки материалов, ссылки, темы и разрешения.
- `chunks.jsonl`: очищенные фрагменты текста со связью на карточки.
- `manifest.json`: версия, SHA-256 исходного снимка, количества и хеши файлов.
- `report.json`: причины исключения, происхождение ссылок, параметры и ограничения.

Временная выгрузка проверяется до публикации каталога версии; при ошибке
частично подготовленный корпус не становится итоговой версией.
При одинаковом снимке и `--as-of` JSONL и manifest воспроизводимы.

## Логика обработки

1. Публикация определяется справочником `Statuses`, а не датой в одиночку.
   Удалённые, закрытые, будущие и неоднозначные материалы исключаются.
   Для статей дополнительно требуется `IsPublic=true`.
2. Полные URL берутся из исходного поля либо из настоящих абсолютных ссылок
   внутри выгрузки. Для slug требуется совпадение вида материала и пути.
   Адреса не достраиваются по догадке и не проверяются сетевым обходом сайта.
   Вебинар с регистрацией/паролем исключается. Для калькулятора требуется
   однозначная опубликованная запись `ContentSettings`.
3. Курсы по подписке и неизвестного типа исключаются. `Cost=null/0` даёт
   `isPaid=false`, но не отменяет остальные проверки доступа и тарифов.
   Для опубликованного платного курса допускается только карточка описания.
4. Урок допускается только при открытых бесплатных родительских курсах.
   Проверяются все активные связи и вся цепочка родительских групп,
   закрытие и `ClosedUntil`. При неоднозначности урок исключается.
   URL урока может быть подтверждённой страницей его курса.
5. Текст собирается из `*EmbedItems`, сортируется по `Order` и ID.
   Из `Params` извлекаются только известные текстовые блоки: врезки, цитаты,
   списки, пояснения. Реклама, видео, изображения, файлы, опросы и карточки
   перехода не выдаются за содержимое материала.
6. HTML превращается в текст с сохранением абзацев, заголовков, списков и ячеек
   таблиц. Удаляются скрипты, оформление, base64, невидимые служебные символы
   и одинаковые блоки внутри одного материала.
7. Разбиение идёт по абзацам, предложениям и словам: цель 2400 символов,
   максимум по контракту 6000, минимум 30. Это ориентир, **не точный подсчёт
   токенов**. Перекрытия нет. При индексации `truncate=false` не позволяет
   тихо обрезать вход модели. `heading=null`: заголовки сохранены в тексте,
   отдельная привязка заголовка к каждому фрагменту пока не делается.
8. UUIDv5 и SHA-256 формируются по `docs/contracts/data/README.md`.
   Нетекстовые материалы могут иметь `answerAllowed=false` и оставаться
   карточками для рекомендаций.

Для документов и глоссария отдельного поля цены в исходной схеме нет:
используются опубликованный статус, отсутствие удаления/конфликтов в
`ContentSettings` и подтверждённая ссылка. Это правило необходимо пересмотреть,
если организаторы предоставят дополнительные ограничения доступа.

## Права и хранение

`externalMetadataAllowed=false` и `externalTextAllowed=false` у **всех** записей:
в предоставленных данных нет подтверждения разрешения внешней передачи.
Такой корпус используется локально. Runtime запрещает удалённый адрес Ollama,
редиректы, HTTP-прокси и облачные модели. Для внешнего API потребовалось бы отдельно
согласовать материалы и расширить политику доступа.

`data/source/` и `data/processed/` уже исключены корневым `.gitignore`.
Не публикуйте snapshot, JSONL, report с реальными ID/ссылками и исходный бэкап.
В Git идут только ML-код, README и синтетические тесты. Ключи не нужны,
поэтому отдельного `env.example` на этом этапе нет.

- Локальный `report.json` с исключениями и ограничениями.
- Следующие задачи: независимая разметка, калибровка порога, сравнение моделей,
